# Edge Functions do Supabase em produção

O workflow [**Supabase Edge Functions Deployment**](../.github/workflows/supabase-edge-functions.yml) publica uma função por execução manual a partir de `main`. A validação usa o mesmo commit da publicação, confere o entrypoint com Deno e roda os testes do handler com serviços simulados. Só depois o job de publicação solicita a aprovação do environment `production`. A CLI oficial do Supabase **2.54.11** envia o código para empacotamento pela Management API (`--use-api`), usando um runner padrão do GitHub Actions, sem Docker ou serviço pago adicional.

## Configuração inicial

1. No GitHub, abra **Settings → Environments → production**. Confirme as proteções existentes de revisão humana e restrição a `main` descritas no [guia de migrações](SUPABASE_MIGRATIONS.md#configuração-inicial). Se a proteção estiver indisponível, suspenda a publicação.
2. Em **Environment variables → Add environment variable**, cadastre `SUPABASE_PROJECT_REF` com o **Reference ID** do projeto Supabase de produção, disponível nas configurações gerais do projeto. O identificador tem 20 letras minúsculas e pode ser tratado como variável de configuração.
3. No Supabase, em **Account → Access Tokens**, gere um token de acesso pessoal (PAT) para esta automação com a menor validade operacional disponível. Use uma conta com o papel **Developer**, que permite publicar e atualizar Edge Functions. O PAT herda os acessos da conta e o papel Developer também permite outras operações sobre o conteúdo do projeto. Se o plano permitir papéis por projeto, limite a conta ao projeto de produção. No plano Free, use Developer no nível da organização, de preferência com uma conta dedicada com acesso apenas à organização necessária. [Tokens da Management API](https://supabase.com/docs/reference/api/introduction) · [Papéis e permissões do Supabase](https://supabase.com/docs/guides/platform/access-control#edge-permissions)
4. No GitHub, em **Settings → Environments → production → Environment secrets → Add environment secret**, cadastre o PAT como `SUPABASE_ACCESS_TOKEN`. Ao rotacionar, atualize esse secret e revogue o token substituído no Supabase. O job disponibiliza o PAT somente no passo que chama a CLI e omite a saída bruta desse comando dos logs.

`RESEND_API_KEY`, `INVITATION_APP_ORIGIN` e `INVITATION_FROM_EMAIL` já estão cadastrados no Supabase de produção e devem ficar apenas lá. O Supabase fornece as chaves do projeto ao runtime da função. Para esta publicação, o GitHub precisa apenas do identificador do projeto e do PAT da Management API.

## Publicação e verificação

1. Após revisão e merge humano, confirme que a migração exigida pela função está aplicada e que os secrets de runtime pertencem ao projeto escolhido. Combine a janela com o responsável pelas migrações. Os jobs de produção dos dois workflows compartilham o mesmo grupo de concorrência. O GitHub mantém a execução em andamento e pode substituir uma execução que ainda esteja pendente. Aguarde a conclusão antes de disparar outra.
2. Em **Actions → Supabase Edge Functions Deployment → Run workflow**, selecione `main` e `send-group-invitation`. Após a validação, o revisor confere o SHA, a função escolhida e o projeto de destino antes de aprovar em **Review deployments → production**.
3. Confira a conclusão do job e a versão da função em **Supabase Dashboard → Edge Functions**. Registre o SHA do GitHub e a versão publicada para eventual recuperação. Para `send-group-invitation`, confira que a verificação legada de JWT no gateway está desativada. O handler deve continuar validando a identidade via `/auth/v1/user`, recusando sessões inválidas, anônimas e de serviço antes das operações privilegiadas. O banco confere se o usuário é administrador do grupo. [Autenticação no gateway e no handler](https://supabase.com/docs/guides/functions/auth-headers)
4. Faça a verificação hospedada com a origem aprovada. Confirme que o `POST` sem sessão válida recebe `401` e que um participante autenticado recebe `403`, sem emissão. Com um administrador e endereço de teste autorizado, confirme a entrega e o aceite do convite. Consulte o [roteiro de convites](INVITATIONS.md#implantação-e-verificação) e preserve credenciais e links reais fora dos logs e registros do PR.

## Recuperação

1. Se a validação falhar, corrija o código em PR e publique a partir da `main` revisada. Se a publicação falhar ou expirar, consulte primeiro a versão e o horário da última publicação no Supabase. Uma falha de comunicação pode ocorrer após a API aceitar a solicitação. Confira a configuração do environment, a validade e o papel do PAT e a referência do projeto. Se a causa continuar incerta, reproduza em um projeto de teste com credenciais próprias e consulte o erro em um terminal restrito.
2. Se a versão publicada estiver incorreta e houver uma versão conhecida como boa, use o SHA registrado para restaurar o código e a configuração JWT da função em um PR para `main`. Confira a compatibilidade da versão restaurada com o schema e os secrets atuais. Em uma primeira publicação sem versão anterior, corrija o problema em um novo PR.
3. Após a correção de configuração ou o merge humano da correção de código, confirme o SHA e inicie um novo **Run workflow → main** para a mesma função, com aprovação no environment `production`. **Re-run jobs** reutiliza o SHA original. Confirme a versão e repita a verificação hospedada. A recuperação deste workflow se aplica ao código e à configuração da Edge Function. [Reexecuções no GitHub Actions](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)

## Inclusão de funções

Inclua o nome nas opções de `workflow_dispatch` e no `case` de validação do workflow. Adicione a checagem do entrypoint e os testes específicos da função, inclusive da autorização, e defina explicitamente `no_verify_jwt` para ela. Use `true` apenas quando a função depender de validação de identidade no handler, como ocorre em `send-group-invitation`. Documente os pré-requisitos de banco, as variáveis de runtime mantidas no Supabase e a verificação pós-publicação.
